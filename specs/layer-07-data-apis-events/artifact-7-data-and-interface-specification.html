The reference, identity and configuration tables (Figure 2) follow the same rules. Their columns are in the gap review (F3–F5). Every change to them writes a platform event with before and after values.

Key constraints in SQL

-- One open incident per alert key (Q7.20). A second insert conflicts and becomes evidence.
CREATE UNIQUE INDEX incident_open_key ON incident (service_id, environment_id, alert_rule)
  WHERE status NOT IN ('closed','cancelled') AND alert_rule IS NOT NULL;

-- One active diagnosis per incident (Q7.19).
CREATE UNIQUE INDEX diagnosis_active ON diagnosis (incident_id) WHERE status = 'active';

-- An approval can be used once (Q7.23, A5 SC-14).
CREATE TABLE approval_use (approval_id uuid PRIMARY KEY REFERENCES approval(id), used_at timestamptz NOT NULL,
  execution_attempt_id uuid NOT NULL);

-- Only a user with the approver role can approve (F1, A5 SC-04).
ALTER TABLE event ADD CONSTRAINT approve_by_approver CHECK (type <> 'action.approved'
  OR (actor_type = 'user' AND actor_role = 'approver'));

-- Immutable tables reject UPDATE and DELETE (Q7.21).
CREATE TRIGGER event_no_change BEFORE UPDATE OR DELETE ON event
  FOR EACH ROW EXECUTE FUNCTION reject_change();

-- Compare-and-set state change (Q7.25). 0 rows = someone else changed it first.
UPDATE incident SET status = :new, version = version + 1 WHERE id = :id AND version = :expected;

7.3Pydantic contracts

Answers: Q7.3, Q7.4, Q7.8, Q7.10, Q7.14, Q7.26, Q7.28

Every API body, event payload and JSONB column has one Pydantic model. The model has a schema_version. The same models validate the input, generate the OpenAPI document, and check the JSONB columns. Unknown fields are rejected (extra = "forbid").

class Actor(BaseModel):                      # F1: on every event
    actor_type: Literal["user", "agent", "platform", "external"]
    actor_id: str                            # user ID, model_call ID, component, integration ID
    actor_role: str                          # approver, diagnoser, executor, monitoring ...
    on_behalf_of: Ref | None = None
    auth_method: Literal["password", "sso", "webhook_hmac", "webhook_token", "sns_signature", "internal"] | None
    session_id: UUID | None = None
    request_id: str | None = None
    reason: str | None = None                # required for cancel, take-over, reject, severity, config change

class AlertIn(BaseModel):                    # Q7.28: what every source adapter produces
    source: str; external_alert_id: str | None; fingerprint: str
    status: Literal["firing", "resolved"]
    service: str; environment: str; alert_rule: str
    severity: Literal["SEV1", "SEV2", "SEV3"] | None

    service: str; environment: str; symptom: str

The patch contract (Q7.8) holds the base commit, branch, head SHA, PR URL, counts and the diff artifact ID. The diff itself is never inline. The approval contract (Q7.10) is the approval row in section 7.2.

Temporal history is not the timeline (Q7.53). It holds engine internals: retries, timers and signal names. It changes when workflow code changes, has its own retention, and is not redacted. Using it would tie the public API to the engine. The platform writes its own domain events.

7.6Event sequencing rules

Answers: Q7.25, Q7.47 to Q7.50

#RuleQ
S1Order is per stream: one stream per incident, plus one platform stream. There is no global order, because it would put every write through one point.Q7.48
S2The writer takes a per-stream lock, reads the last sequence and hash, and inserts sequence + 1 with the new hash, in one transaction. The lock also keeps the hash chain without forks.Q7.47
S3Order by sequence, never by a timestamp. Clocks drift. occurred_at and recorded_at are both kept for people.Q7.47
S4A state change and its event are one transaction. The event carries the new incident.version.Q7.25
S5A consumer keeps its last sequence for each stream in consumer_checkpoint. It skips a sequence at or below that value. Handlers are idempotent by event ID.Q7.49
S6Gap check: if a consumer gets sequence n and n > last + 1, it reads ?after=last first. It applies events only in order.Q7.50
S7Lists across incidents sort by recorded_at. This order is approximate and is for display only.Q7.48

7.7Outbox design

Answers: Q7.54 to Q7.59, Q7.64

A PostgreSQL transaction cannot include Temporal. Temporal has its own storage, and there is no two-phase commit between them (Q7.56). So the platform uses a transactional outbox (Q7.57). The platform has two outboxes and no new table:

OutboxMarker written in the same transactionRelayOutside effect
Start a workflowincident.status = 'queued'Admission loop (worker)Temporal workflow start
Tell the outside worldThe event rowConsumers with consumer_checkpointSSE, chat, pager, ticket updates

Figure 3. Outbox sequence for incident A. The workflow starts only after the incident row commits, so a workflow without an incident cannot exist (Q7.55). A crash between steps 5 and 8 is safe (Q7.59).

CaseWhat happensQ
Temporal is down after the incident is savedThe incident stays queued. The loop retries with backoff. A platform alert fires when an incident stays queued past a set time.Q7.54
Workflow starts, but the incident row is missingNot possible in this order. If it happens, the first step finds no incident, fails, and raises a platform alert.Q7.55
Find pending workSELECT … WHERE status = 'queued' ORDER BY severity, created_at FOR UPDATE SKIP LOCKED LIMIT n. LISTEN/NOTIFY only wakes the loop.Q7.58
Crash after start, before the updateStart again with the same workflow ID. "Already started" means success.Q7.59
KafkaNot in V1. PostgreSQL and the outbox carry about 3 incidents with tens of events each. Use Kafka only when one of these is measured: many independent consumer systems need fan-out and replay; thousands of events per second slow PostgreSQL; consumer lag passes a set limit; events must cross data centres.Q7.64

7.9SSE timeline design

Answers: Q7.30, Q7.51 to Q7.53

The timeline is a read view over the event table in sequence order. There is no separate timeline table. Every event names its subject record and its cause. So a click on one item returns the full provenance chain: action → diagnosis → hypotheses → evidence → tool calls and model calls → approval → attempts → verification (Q7.30). A projection table is added only if the provenance query misses its latency target (Layer 12-A).

Figure 5. SSE resume. The event ID holds the stream and the sequence. On reconnect the server replays from the next sequence, so the client loses nothing. Events are kept for one year.
