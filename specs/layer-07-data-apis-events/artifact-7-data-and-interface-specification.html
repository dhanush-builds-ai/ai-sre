7.1Entity relationship diagram

Answers: Q7.1, Q7.2, Q7.5 to Q7.9, Q7.18, Q7.19, Q7.22

The platform has 29 tables in 7 groups (Q7.18). Each table holds one kind of record. A table exists only when its rows need their own key, their own write rule or their own foreign keys. Figure 1 shows every table, its keys and every foreign key. The ID of every record is a UUIDv7. A UUIDv7 sorts by time. The incident ID is also the Temporal workflow ID (A6 ADR-03).

Why the remaining tables are separate

PairWhy two tablesLabel
hypothesis, diagnosisA hypothesis is one candidate cause. An incident has many, and the ruled-out ones stay for the report (A4 FR-06). A diagnosis is the conclusion that the critic reviews and that an action points to. It can be inconclusive, so it has no hypothesis. It has up to 2 versions (one revision) and the human feedback.Decision
check_result, actionOne action gets several checks (critic, policy, sandbox, verification), and the critic also checks a diagnosis. Each check is an immutable record with its own verdict and evidence. Columns on action would be overwritten by a re-run.Decision
approval, execution_attemptThe approval is the human's signed decision. An attempt is one dispatch to production. A re-dispatch after reconciliation is a second attempt with the same approval (A8 8.9).Decision
platform_setting, eventThe setting row holds the current value and a pending change. The history of every change is the config.proposed and config.changed events, with before and after values (A5 AST-11).Decision
Not in the database: workflow progress (Temporal); prompts, policy rules, redaction rules and the tool allow list (repository, reviewed PR, A5 AST-10); secrets and signing keys (secret store; the database keeps only the reference name).

Key constraints in SQL

-- One open incident per alert key (Q7.20). A second insert conflicts and becomes evidence.
CREATE UNIQUE INDEX incident_open_key ON incident (service_id, environment, alert_rule)
  WHERE status NOT IN ('resolved','cancelled') AND alert_rule IS NOT NULL;

-- One incident per engineer submission (Q7.61, A4 NFR-01).
CREATE UNIQUE INDEX incident_submit_key ON incident (created_by_user_id, idempotency_key)
  WHERE idempotency_key IS NOT NULL;

-- One active diagnosis per incident (Q7.19).
CREATE UNIQUE INDEX diagnosis_active ON diagnosis (incident_id) WHERE status = 'active';

-- One open approval per action; an approval is used by one first dispatch only (Q7.23, A5 SC-14).
CREATE UNIQUE INDEX approval_one_pending ON approval (action_id) WHERE status = 'pending';
CREATE UNIQUE INDEX approval_single_use ON execution_attempt (approval_id) WHERE attempt_no = 1;

-- Second admin (A5 SC-24): the approver must differ from the proposer. 0 rows = refused.
UPDATE platform_setting SET value = pending_value, version = version + 1, pending_value = NULL,
  pending_by_user_id = NULL, pending_reason = NULL, pending_at = NULL
  WHERE key = :key AND pending_value IS NOT NULL AND pending_by_user_id <> :approver;

-- Backstop only: an approval event must name a user in the approver role (F1, A5 SC-04).
-- The real check is the decisions endpoint: it reads ownership and on-call at decision time
-- and stores the result in approval.role_at_decision.
ALTER TABLE event ADD CONSTRAINT approve_by_approver CHECK (type <> 'action.approved'
  OR (actor_type = 'user' AND actor_role = 'approver'));

-- Immutable tables: no UPDATE; DELETE only by the maintenance role (Q7.21, S1).
CREATE TRIGGER event_no_change BEFORE UPDATE OR DELETE ON event
  FOR EACH ROW EXECUTE FUNCTION reject_change();   -- allows DELETE when current_user = 'ai_sre_maintenance'

-- Compare-and-set state change (Q7.25). 0 rows = someone else changed it first.
UPDATE incident SET status = :new, version = version + 1 WHERE id = :id AND version = :expected;

An action run inserts execution_attempt (intent, attempt 1) before dispatch. The partial unique index makes this insert the single use of the approval. A re-dispatch after reconciliation (attempt 2) uses the same approval, because it continues the approved execution (A5 SC-16).

7.3Pydantic contracts

Answers: Q7.3, Q7.4, Q7.8, Q7.10, Q7.14, Q7.26, Q7.28

Every API body, event payload and JSONB column has one Pydantic model. The model has a schema_version. The same models validate the input, generate the OpenAPI document, and check the JSONB columns. Unknown fields are rejected (extra = "forbid").

class Actor(BaseModel):                      # on every event
    actor_type: Literal["user", "agent", "platform", "external"]
    actor_id: str                            # user ID, model_call ID, component, integration ID
    actor_role: str                          # approver, diagnoser, executor, monitoring ...
    on_behalf_of: Ref | None = None
    auth_method: Literal["password", "sso", "webhook_hmac", "webhook_token", "sns_signature", "internal"] | None
    session_id: UUID | None = None
    request_id: str | None = None
    reason: str | None = None                # required for cancel, take-over, reject, severity, config change

class AlertIn(BaseModel):                    # Q7.28: what every source adapter produces
    source: str; external_alert_id: str | None; fingerprint: str
    status: Literal["firing", "resolved"]
    service: str; environment: str; alert_rule: str
    severity: Literal["SEV1", "SEV2", "SEV3"] | None
    starts_at: datetime; summary: str; labels: dict[str, str]

class IncidentSubmit(BaseModel):             # engineer submission (FR-01)
    service: str; environment: str; symptom: str
    started_at: datetime; severity: Literal["SEV1", "SEV2", "SEV3"] | None = None

class LogEvidence(BaseModel):  kind: Literal["log"];    lines: int;  sample: list[str]
class MetricEvidence(BaseModel): kind: Literal["metric"]; series: str; points: list[tuple[datetime, float]]
class TraceEvidence(BaseModel): kind: Literal["trace"];  trace_id: str; spans: int; error_spans: int
class ConfigChangeEvidence(BaseModel): kind: Literal["config_change"]; key: str
    from_version: str; to_version: str; value_changed: bool   # secret values never read (A1 E8)
EvidencePayload = Annotated[LogEvidence | MetricEvidence | TraceEvidence | ConfigChangeEvidence | ...,
                            Field(discriminator="kind")]       # Q7.3, Q7.26

class EvidenceRecord(BaseModel):             # Q7.4
    id: UUID; incident_id: UUID; kind: str
    source: str; adapter_version: str; query: dict   # holds the time window
    collected_at: datetime; content_hash: str; artifact_id: UUID | None
    redaction_version: str; status: Literal["ok", "partial", "missing"]
    payload: EvidencePayload                 # always untrusted (A9 9.4)

class Decision(BaseModel):                   # Q7.32, Q7.33
    decision: Literal["approve", "reject"]
    action_hash: str                         # must equal the current action hash (A5 SC-14)
    reason: str | None                       # required for reject and self-approval
    password: SecretStr | None               # re-entry in own-login mode (A5 SC-25)

class ModelCallRecord(BaseModel):            # Q7.14
    role: Literal["investigator", "diagnoser", "critic", "fixer"]; model_name: str; model_version: str
    prompt_version: str; input_hash: str; input_tokens: int; output_tokens: int
    latency_ms: int; attempt: int; result: Literal["valid", "malformed", "timeout", "refused", "error"]; gateway_status: str
    stop_reason: Literal["finished", "tool_call", "token_limit", "refused", "none"]

class Problem(BaseModel):                    # RFC 9457, Q7.38
    type: str; title: str; status: int; detail: str; request_id: str

Figure 2. Pydantic contracts. Each caller produces one contract. Every source adapter maps its payload to AlertIn. The server fills the Actor block; a request body cannot set it. The same model validates the body, generates OpenAPI and checks the stored JSONB.

The patch contract (Q7.8) holds the base commit, branch, head SHA, PR URL, counts and the diff artifact ID. The diff itself is never inline. The approval contract (Q7.10) is the approval row in section 7.2.

7.4API specification

Answers: Q7.28 to Q7.41

RuleDetail
VersioningThe URL holds the version (/v1). Changes in a version only add. A breaking change gets /v2 and a deprecation period. CI compares the generated OpenAPI document and flags a breaking change (Q7.40).
AuthenticationA session or bearer token gives the user. The dashboard keeps the same session in an HttpOnly cookie and sends a CSRF token with every write (A5 SC-26). One login mode for each deployment: own login (default) or SSO (A5 SC-25). Webhooks use the auth method of their source (Q7.39).
AuthorizationEach endpoint states its role. The server checks it on every request from team membership and on-call at that time (A5 SC-03). Admin endpoints are under /v1/admin and need the separate admin account (F3).

ErrorsRFC 9457 application/problem+json. 401 = not logged in. 403 = no right, with an audit event. 409 = state or hash conflict. 422 = invalid body, or an idempotency key reused with a different request (Q7.38, Q7.62).

7.7Outbox design

Answers: Q7.54 to Q7.59, Q7.64

A PostgreSQL transaction cannot include Temporal. Temporal has its own storage, and there is no two-phase commit between them (Q7.56). So the platform uses a transactional outbox (Q7.57). It has one outbox and no new table:

Figure 5. Outbox sequence for incident A. The queued incident row is the outbox marker. The workflow starts only after the row commits, so a workflow without an incident cannot exist (Q7.55). A crash between steps 5 and 8 is safe (Q7.59).

7.9SSE timeline design

Answers: Q7.30, Q7.51 to Q7.53

The timeline is a read view over the event table in sequence order. There is no separate timeline table. Every event names its subject record and its cause. So a click on one item returns the full provenance chain: action → diagnosis → hypotheses → evidence → tool calls and model calls → approval → attempts → verification (Q7.30). A projection table is added only if the provenance query misses its latency target (Layer 12-A).

Figure 7. SSE start and resume. The first request has no Last-Event-ID, so the server sends the timeline from sequence 1. The event ID holds the stream and the sequence. On reconnect the server replays from the next sequence, so the client loses nothing.
