Own GPUs at small volume (Q10.7). A small volume does not justify an own GPU cluster by cost. Only control needs justify it. There are five such needs. Data must not leave the organization. A custom model needs a host that no provider offers. The team needs strict control of model versions. The latency or the network has special needs. A firm plan exists for a large, steady volume. V1 does not meet these needs by default, so the default is a cloud provider. An organization that must keep data inside enables the self-hosted option on GPUs that it already owns.

Serving engine candidates (Q10.8)

The self-hosted option needs a serving engine that runs two models on the existing GPUs. The engine must manage GPU memory and batch requests. It must offer an OpenAI-compatible HTTP interface, because the gateway adapter uses it (L6-A2). The KV cache saves compute time. It uses GPU memory. It does not save memory.

10.2Model gateway contracts

Answers: Q10.9, Q10.10, Q10.11, Q10.12, Q10.13, Q10.14, Q10.15, Q10.16, Q10.17, Q10.18, Q10.19, Q10.20, Q10.21, Q10.22, Q10.23

The agent never talks to a model server. Every agent model points at the inference gateway. The gateway is the only path to a model (Artifact 6, Q6.12). It gives one interface for all models. A change of model is a configuration change (Artifact 2, 2.5).

Figure 2. Component diagram of the inference gateway. The agents see one contract. The adapters hide the model server. Dashed parts are off by default or not in V1. Every cloud host follows the cloud rules (10.3).

Who owns what (Q10.9)

OwnerResponsibilities
Inference serviceRun the model. Serve requests. Report token usage.
Application (gateway)Build requests in our format. Reserve budget. Enforce the timeout. Write the model_call record. Choose model and parameters. Parse and validate responses. Account for tokens. Log provenance.
Tool layer (Artifact 9)Validate and run the read tool requests of the agents. No agent has a write tool.
Workflow (Artifact 8)Retry, escalate, and decide what happens next.

Server differences stop at the adapter. So the agents see the same behavior for every model. Model output is untrusted data (Artifact 6, trust zones). The gateway validates it before the platform uses it.

Adapter rules (Q10.10, Q10.11, Q10.12)

  • The gateway has two thin adapters, on the official OpenAI and Anthropic SDKs (Artifact 6, Q6.28). Each implements the contract. The Anthropic adapter serves the default cloud provider. The OpenAI-compatible adapter serves the self-hosted engine or an OpenAI-compatible cloud host.
  • All server-specific code stays in the adapter. This includes client calls, authentication, formats, error types, and model IDs.
  • The agent must not import server-specific code.
  • The adapter converts every response to the internal structure. A tool request has an id, a tool name, and parsed arguments.
  • The adapter flags malformed output. It must not pass it on silently.
  • The model client does not retry (max_retries = 0). Temporal is the only retry owner (Artifact 8, 8.5).
  • The gateway keeps the raw response and the redacted raw request as artifacts. The model_call record points to both (output_artifact_id, request_artifact_id).
  • Only redacted content reaches a model (Artifact 5, SC-09). If the redactor fails, the evidence counts as missing. Nothing goes out raw.
  • Contract tests check that every adapter behaves the same way.

Capability incompatibility (Q10.22)

The gateway keeps the capability matrix (10.1). Before it sends a request, it checks the capabilities that the role needs. If a model lacks one, the gateway follows these rules in order.

  1. Emulate the capability only where the configuration allows it. Native tool calling is never emulated (L9-A1).
  2. Otherwise reject the configuration at start. The platform does not start with it.

Emulation is explicit configuration. It is never silent. The gateway never sends a request to a model other than the one configured for the role. There is no automatic fallback (A2 2.5, A5 SC-24).

No automatic fallback (Q10.39)

Artifact 2 decides this (2.5). The platform has no CPU fallback and no automatic fallback from one provider to another. A model server counts as down after the last attempt fails: the model_request timeout and 1 retry (Artifact 4, QR-03, NFR-12). Then the platform halts. It escalates to a person with the alert and the evidence so far. Escalation is plain system logic. It needs no model.

An automatic fallback has these risks:

  • A different model behaves differently. Prompts for one model may fail on another.
  • The other model may lack a required capability.
  • Data would go to another provider. The organization has not approved it.
  • Costs differ.
  • All requests arrive at once and overload the second server.
  • Tracing gets harder.

High availability reduces the need for a fallback.

Figure 6. Decision tree for a failed model call. Only temporary errors are retried, only by Temporal, and only while attempts and time remain. After the last attempt the server counts as down, and the platform halts and escalates. Malformed output is asked again, at most 3 times.

Sources and ingestion (Q10.40, Q10.42)

  1. Collect the documents. Runbooks come from the knowledge repository in Git (Artifact 7, knowledge_document). Past incidents come from the platform database.
  2. Read and clean the text. Keep the headings and code blocks.
  3. Split the text into chunks by heading (10.10).

  6. Check the result with counts and sample searches.
  7. Run again when a commit changes a document. A removed document gets the status removed.
