At a glance

Figure 1. Layer 10 at a glance. Every model request goes through the inference gateway and a PydanticAI model client. Two providers are on: Anthropic for the main model and OpenAI for the reviewer model. Other clouds are supported in code and off. Self-hosted vLLM is designed and off. Tinker is not used. Runbooks, past incidents and full logs are searched, then context assembly builds each request. The limits and the items outside V1 are at the bottom.

10.1Provider capability matrix

Answers: Q10.1 to Q10.9, Q10.24

A large language model (LLM) turns input tokens into generated tokens, one token at a time (Q10.1). The model is the trained weights, for example Claude Opus. The provider runs the model and exposes an API, for example the Anthropic API, AWS Bedrock or our own vLLM server (Q10.2). One model can come from several providers. Data terms, rate limits, prices and the API format belong to the provider. So the configuration and every model_call row keep both the provider and the exact model ID.

Exact model IDs are pinned. An alias such as "latest" is never used. A provider is enabled only when it is on the approved list in configuration. The A2 rules apply: two admins, a reviewed config change, the key in the secret store and the host on the egress allow list (A2 2.5, A5 SC-24).

10.2Model gateway contracts

Answers: Q10.10, Q10.13 to Q10.16, Q10.21, Q10.23

The inference gateway is the only path to a model (A6 ADR-06). It does not have its own client for each provider. It wraps the PydanticAI model client of the configured provider. In flight, the interface is the PydanticAI message types, which the agents already use (A9). Everything that is stored is in our own format: model_call, the request and output artifacts and budget_entry (A7).

Figure 3. One model call. The gateway checks the allow list, redacts and reserves the worst-case cost before any outside call. It streams the call to the final event and its stop reason. It validates the output, commits the actual cost and writes the records. Then it returns a ModelResult. A reservation that does not fit stops the call.

10.10Chunking strategy

Answers: Q10.43, Q10.44

Figure 8. Heading-aware chunking with a sliding window. A short section is one chunk. A long section is cut into windows of about 400 tokens that overlap by 50 tokens. Every chunk starts with its heading path. A code block or a table stays in one window.

StepRuleQLabel
1 Split at headingsSplit at Markdown headings. A section under the limit is one chunk.Q10.43, Q10.44Decision
2 Window a long sectionCut a longer section into windows of about 400 tokens with 50 tokens of overlap. The overlap keeps a step with the sentence before it.Q10.43Decision Assumption L10-A8
3 Add the heading pathEach chunk starts with its heading path, for example "Payments runbook > Rollback > Config errors". So an instruction keeps its heading, and BM25 also matches heading words.Q10.44Decision
4 Keep blocks wholeNever split inside a code block or a table. The window boundary moves.Q10.44Decision
5 LocationEach chunk keeps its first and last line in the document, for the citation (10.9).Q10.53Decision

Chunks are not stored. Chunking is deterministic: the same document text and the same platform build give the same chunks. So each worker makes the chunks from the stored documents when it builds its index.
