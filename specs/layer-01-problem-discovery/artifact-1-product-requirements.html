1.1Problem statement

Answers: Q1.1, Q1.3, Q1.4, Q1.7, Q1.8

Alert systems already work. When a service fails, the existing alert system sends a message to people. The message can be an email, a chat message, or a ticket.

The unsolved problem is what happens after the alert. The engineer must restore the service and find the cause by hand. This takes a long time, and the work is tiring.

What the engineer does today

  1. Read the alert. See which rule or limit it broke.
  2. Collect logs.
  3. Look at recent changes and who made them.
  4. Look at past incidents and knowledge documents.
  5. Join all of this information in their head.
  6. Form a hypothesis about the cause.
  7. Decide how to restore the service.

Figure 1. The incident flow today and with the platform.

What information the engineer needs to find the root cause

  • The alert and the rule or limit it broke.
  • Logs and metrics.
  • Recent changes, with the author of each change, and the difference in configuration.
  • Past incidents that look the same.
  • Knowledge documents.
  • The health of other services that this service depends on.

Today this information is in different places. This is the main reason why diagnosis is slow.

Why the problem matters

WhoEffect of a long outage
UsersEffect depends on the service. A failed payment hurts users and the business. Any visible failure reduces trust.
BusinessLost income and lost trust. A failure in payments or in a core function is the most serious.
On-call engineerA page at 2 AM causes fatigue and mental strain. A more serious incident gives more pressure and more cognitive load.
Engineering teamMore severe outages take more time and more priority from other work.

The cost of a wrong diagnosis

  • The symptom can go away for a short time and then come back.
  • The real cause stays. The outage can become worse.
  • An unneeded fix can cause new problems.
Problem statement. After an alert, engineers spend too much time collecting scattered evidence by hand, restoring the service, and finding the cause. A wrong diagnosis makes the incident worse. The product must reduce the time to recover and increase the accuracy of the diagnosis. It must make no production change without human approval, and every change must have an undo path.

How the platform finds the right owner

  • The platform keeps a maintained list: service → owning team → manager → team members.
  • When an alert arrives, the platform looks up the failed service in this list.
  • The platform reads the on-call schedule. It sends the incident to the owning team and to the person on call.
  • The author of a recent change is shown as evidence only. The platform does not give the incident to this person.
Unmapped services. A service can have no owner in the list, or the list can be old. The fallback is not decided yet (see assumption A3).

1.3User journey

Answers: Q1.4, Q1.9, Q1.20, Q1.21. Reference scenario: a deployment changes a configuration value, and the application returns HTTP 500 errors.

Figure 2. Swimlane diagram, phase 1: recovery. Yellow = human. Blue = platform. Green = service recovered.

Figure 2b. Swimlane diagram, phase 2: permanent fix. The fix is proven, reviewed, and approved before it is applied.

The journey in the reference scenario

  1. A deployment changes a configuration value. The application starts to return HTTP 500 errors.
  2. The monitoring system detects the incident and sends an alert. The alert gives the initial severity.
  3. The platform listens for alert events. It groups related alerts into one incident.
  4. The platform finds the owner of the service and the person on call.
  5. The platform collects the alert details, logs, metrics, recent changes (with the configuration difference), past incidents, and knowledge documents.
  6. In parallel, a human confirms or changes the severity. The platform does not wait for this step.
  7. The platform finds that the errors started after the recent change. It proposes to revert the change to the last known-good version. It shows the evidence and a confidence level.
  8. A reviewer that uses a different model, with a new context, reviews the proposal and looks for faults.
  9. A human approves the revert. If the approver does not answer in a set time, the platform asks the backup approver.
  10. The platform applies the revert.
  11. The platform watches the same signals that caused the alert. It compares them to the normal level before the incident, for a set period.
  12. The service is recovered. The platform continues to find the root cause.
  13. The platform proposes a permanent fix for the root cause. In the reference scenario, this is a correct configuration value.
  14. The platform proves the fix in a non-production copy of the application.
  15. The reviewer that uses a different model reviews the fix.
  16. A human approves the fix. The fix must have an undo path.
  17. The platform applies the fix. It watches the same signals again for the set period.
  18. The platform closes the incident. It writes a report with the root cause, the fix, and the full audit trail.

When something goes wrong

ConditionWhat the platform does
Evidence is not enough (escalation rules or rubric are met)Says clearly that it cannot find the cause. Hands over to a human. Shows what it checked and what is missing.
No recent change matches the errors, or the change cannot be revertedDoes not propose a revert. Hands over the findings. Escalates to a human.
The review rejects the proposalDoes not apply the revert. Reports why. Escalates to a human.
The approver and the backup approver do not answer in the set timeDoes not apply the revert. Escalates.
Errors continue after the revertReports that the change may not be the only cause (the revert can be incomplete, or the configuration may not have reloaded). Keeps the undo path ready. Escalates to a human.
The incident recovers by itself during the investigationMarks the incident "recovered without action". Watches the signals for the set period. Finishes the root-cause report.
The fix fails in the non-production copy, the copy cannot reproduce the problem, or the review rejects the fixDoes not apply the fix. The service stays on the reverted version. Closes the incident with the fix as a recommendation. Tells the owner.
The human declines the fixDoes not apply the fix. Closes the incident with the fix as a recommendation.
Errors return after the fix is appliedUses the undo path of the fix (back to the recovered state). Escalates to a human.
The investigation reaches its limit of time, steps, or costStops. Escalates to a human.
A human stops the platform or takes overStops all actions at once. Hands over the incident record.

How information is kept during the incident

  • The platform writes a provenance record. It lists every resource the platform accessed and what information it fetched.
  • The record is kept in a separate store, so people can trace and audit every claim.
  • There is one record for each incident. People and the platform can only add entries. They cannot change old entries.
  • The record stays after the incident closes.

Secrets and personal data in evidence

  • The platform must not read the value of a secret. It reads only the name of the secret and whether the value changed.
  • To see if a secret changed, the platform compares a fingerprint of the old and new value. It does not compare the values.
  • The platform removes secrets and personal data from logs and other evidence before it stores the evidence, shows it, or gives it to a model.
  • The provenance record keeps the location of each source and the cleaned extract. An engineer with the correct access can open the original source.

1.5Product boundaries

Answers: Q1.6, Q1.10, Q1.11, Q1.14, Q1.15, Q1.21, Q1.22

Assistant or platform?

An ordinary assistantThis platform
Collects, joins, and reasons about evidence.
Gives suggestions.		Does all of that, and acts on the environment, watches the result, and reasons again. It repeats this until the goal is met. Guardrails limit the loop (time, steps, cost). It verifies the recovery.

What the platform can do in V1

  • Read: the platform can read evidence from the affected service and from related services.
  • Write: the platform has two production actions in V1, each after human approval: (1) revert the most recent change: redeploy the last known-good version, or restore the previous configuration version in the config store; (2) apply an approved permanent fix (a code or configuration change) that was proven in a non-production copy. Each action has an undo path.
  • Trigger: the platform listens for alert events. It does not depend on one channel (email, chat, or ticket). It can send findings to the channel of the alert and to the incident record.

Human checkpoints (V1)

CheckpointWhy a human is needed
Confirm or change the severity (does not block the platform)Business severity needs human judgment.
Approve every production change (in V1: every revert and every fix)A production change can hurt users. A human must own the risk.

Decision. V1 has no allow list. A human approves every production change, every time. The approver is the on-call engineer or the service owner. The approver can be the author of the change. Rationale: at 2 AM the author is often the only person on call; the other controls still apply (a review by a different model, policy checks, an undo path, and the audit trail). The threat model (Layer 5, Chirag) checks if self-approval must be forbidden for SEV1.

How the platform decides (decision policies)

The platform uses two known decision policies. One sets how careful an action must be. The other sets how deep the reasoning must be.

PolicyQuestion it answersRule in V1
Type 1 / Type 2 decisions (one-way door / two-way door)Can the action be undone?Type 2 (can be undone): reading evidence, a revert, and a permanent fix with an undo path. A revert and a fix still need human approval.
Type 1 (cannot be undone): deletion and irreversible changes. Not allowed in V1.
System 1 / System 2 thinking (fast / slow)How much reasoning does this case need?System 1 (fast): fixed escalation rules (policies) are checked first. Example: no recent change matches the errors, so escalate.
System 2 (slow): when no rule decides, the platform scores the evidence with a rubric that has context and guidance.
Gate: a low rubric score, a new kind of incident, or a conflict in the evidence sends the incident to a human.

Figure 5. Escalation decision flow. Fast rules first (System 1), then a rubric (System 2). Only a Type 2 action is proposed. The same flow applies to a permanent fix.

What gives engineers trust

  • Evidence: every claim has a source in the provenance record.
  • Audit trail: a complete record of what the platform read, said, and did.
  • Honesty: when confidence is low, the platform says so and escalates. It does not guess.
  • Control: no production change without human approval. A human can stop the platform at any step.
  • Independent checks: a reviewer that uses a different model checks every revert and fix. A non-production copy proves every fix. The original signals prove the recovery.
Limitation. A reviewer with a different model reduces shared errors, but it does not remove them. The human approval stays necessary.

1.6Success definition

Answers: Q1.12, Q1.16, Q1.17, Q1.18

Smallest useful product (V1)

V1 is useful when the platform can do these things:

  1. Receive and group alerts, and investigate the incident.
  2. Explain the findings with evidence.
  3. Propose a revert of the recent change, and apply it only with human approval.
  4. Watch the same signals after the revert, and say if the service is recovered.
  5. Find the root cause. Propose a permanent fix, prove it in a non-production copy, and apply it only with human approval. Verify the signals again.
  6. Escalate with a clear explanation when the evidence is not enough.

How we know that a recovery worked

The platform does not use its own claim as proof. After the revert, the platform checks the signals that caused the alert. The error rate must return to the normal level from before the incident. The alert must clear. These must stay true for a set period. period and "normal level": not yet set (C4, E4)

Low traffic (for example at 2 AM) can make a failed service look healthy. The check must consider the traffic level.

Plan: measure the baseline from past incidents. If there are no past incidents, an engineer handles the reference scenario by hand, and we measure the time. Then we set the targets.

Demonstration

Use the reference scenario. Show these steps in order: alert, alerts grouped, owner found, evidence shown, hypothesis with confidence, revert proposed, review by a different model, human approval, revert applied, signals watched until healthy. Then: root cause found, permanent fix proposed and proven in a non-production copy, fix reviewed, fix approved, fix applied, signals watched again, report and audit trail.

Then do a second, short run with missing evidence. Stakeholders must see the platform say "not enough information" and escalate.

1.7Explicit non-goals

Answers: Q1.19

The platform must never

  1. Make a production change or deployment without human approval.
  2. Leak sensitive data or secrets.
  3. Write to any service other than the affected service. (Reading related services is allowed.)
  4. Delete data.
  5. Turn off or silence alerts and monitoring.
  6. Change access or permissions.
  7. Claim success without independent verification.
  8. Apply a change that has no undo path. (Irreversible changes are not allowed in V1.)
  9. Take silence as approval.

The product is not

  • A replacement for the alert system. The existing alerts are the trigger.
  • A replacement for engineers. Humans keep every judgment and approval.
  • An autonomous system. V1 does not change production by itself.

Tools, environments, and limits (language, cost, number of incidents) are for Layer 2.
