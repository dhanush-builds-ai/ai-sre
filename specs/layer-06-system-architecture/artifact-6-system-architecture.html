6.2Container/process diagram

Answers: Q6.1 to Q6.4, Q6.8, Q6.26, Q6.35, Q6.38

The platform is one repository and one image. It runs as four process types: API, worker, executor and sandbox runner (Q6.8, Q6.38). Each process is a separate container. The processes do not call each other. They share work only through PostgreSQL and the Temporal task queues (Q6.8).

Figure 2. Container diagram. Blue = platform processes from one image. Purple = data stores. The executor and the sandbox runner are Temporal workers on their own task queues, so the worker never calls them directly.

Figure 3. Sequence for incident A (Q6.35). Steps 1 to 4 run inside the request (A4 Q4.19: p95 ≤ 30 s). Step 3 saves and queues in one transaction. A second start in step 6 does nothing, because the workflow ID is the incident ID.

Admission: how the queue works

  1. Intake saves the incident with status "queued". The save and the queue entry are one transaction (Q6.1).
  2. The admission loop counts the running incidents. If the count is less than the limit (3, configurable), it selects the next "queued" incident by severity, then by age (A4 NFR-07).
  3. It starts a Temporal workflow. The workflow ID is the incident ID. A second start of the same incident does nothing.
  4. If 20 incidents wait, a new incident goes to humans and is not dropped (A4 QR-07).
  5. Recovery work comes before fix-phase work. Layer 8 designs how the workflows do this.
No Celery, no RQ (Q6.26). Temporal already has durable task queues. A second queue would add a broker and a second record of what is running.

The trust zones come from Artifact 5 (Figure 1, TB-1 to TB-6). This section places them on the containers. A container that runs untrusted code or holds a production credential is a separate container (Q6.5 rule).

Figure 5. Deployment view with trust zones. Solid boxes are containers. "key" marks a container that holds a credential. Red circles are the A5 trust boundaries TB-1 to TB-6. The sandbox runner and the executor are separate containers because each is a security boundary.

Figure 6. Sequence from sandbox result to production action (Q6.37). The sandbox runner sends only a test report. It has no message to the approval gate or the executor. The critic's verdict is a signal, never an authorization. For a fix, the human approver also merges the pull request (A4 FR-11).
