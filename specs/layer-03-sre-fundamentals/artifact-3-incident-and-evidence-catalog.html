3.1Initial alert

Answers: Q3.3, Q3.9, Q3.10, Q3.22

How an alert becomes an incident

  • An alert is not always an incident. A short blip is noise.
  • The team declares an incident when users are affected for longer than a set time: error rate above 2%, or p95 latency above 1 s, for more than 5 minutes (provisional, L3-A2).
  • A shallow health check can pass while real requests fail. User-facing error rate and latency are better signals than the health check.

What the status code tells

StatusMeaning
401, 403Authentication or authorization failed. This is not a 500.
502, 503, 504The proxy cannot reach a healthy application, or the request timed out.
500The application itself failed. Usually an unhandled exception (for example a bad configuration value) or a failed dependency that the code did not handle.

Service level objective (provisional, L3-A2): 99.9% of requests succeed over a rolling 30 days, and p95 latency is below 300 ms.

Severity levels (provisional, L3-A2)

LevelCondition
SEV1Error rate 50% or more, or no successful responses, or a core function (for example payments) is down.
SEV2Error rate 5% to 50%, or p95 latency above 2 s.
SEV3Error rate 2% to 5%, or p95 latency 1 s to 2 s, or few users affected.

Severity also depends on: the absolute count of errors, which endpoints fail (core or not), how many users are affected, how long it lasts, the trend, and how fast the error budget is used (burn rate). A full outage is about 100% of requests failing, or no successful responses. Zero incoming traffic usually points upstream (DNS, load balancer).

3.2Service context

Answers: Q3.1, Q3.2, Q3.4, Q3.5, Q3.29, Q3.32

Figure 1. Component diagram of the request path. Each part can fail in a different way. Incidents A and B fail inside shop-api. Incident C fails in orders.

What the components do

  • Entry point. A load balancer and a reverse proxy (or API gateway) expose the application. Only the needed ports are open.
  • Under load. Components queue requests, pool database connections, scale out behind the load balancer, apply rate limits, and use circuit breakers. Every call has a timeout. Retries use backoff and a limit, or they cause a retry storm. Caches reduce database load.
  • Durable data. Only the database (or object storage, or attached volumes) keeps data after a restart. Caches and container disks lose it.
  • Tools today. Engineers use a dashboard with the golden signals for each service, SLO and error-budget views, deploy markers on graphs, and links from a service to its logs and traces.
  • Integration principle. Each kind of data (logs, metrics, traces, deployments, errors) has one small common interface, with one adapter for each tool.

3.3Logs

Answers: Q3.17, Q3.20, Q3.31

  • What a log record holds. Structured fields: timestamp, severity, service, code and config version, request or trace ID, message, error type, and the full stack trace. Personal data and secrets are removed.
  • Why logs alone are not enough. A log is one record of one event. To know how often a failure happens, you must count and join many logs. This is slow and costly, and logs can be sampled or dropped. Metrics count at the source, so rates are cheap and exact.
  • Error-tracking platform. Read it through its API or webhook, with read-only access. A hosted error tracker that the organization already approved is allowed. The platform reaches it through allow-listed network rules (Artifact 2, review H3).

3.5Traces

Answers: Q3.19, Q3.30

  • A trace ID is passed from service to service in request headers (W3C Trace Context). Each service adds a span with its timing and status. The failing span shows which service failed.
  • Standards: OpenTelemetry for instrumentation, W3C Trace Context for the trace ID, and one structured log format that carries the trace ID, so logs and traces can be joined.

3.6Deployment changes

Answers: Q3.6, Q3.7, Q3.14, Q3.26

  • Deployment steps today. Merge to the main branch, CI/CD runs tests, the pipeline builds one versioned artifact (image), deploys it to staging, QA approves, then the same artifact goes to production. The rollout uses a strategy (rolling, blue-green, or canary) and health checks. Configuration enters at deploy time from the config store or the repository.
  • Deployment record. Each deployment records: time, service, commit or image version, config version, who made it, environment, and rollout status. (Decision; whether all of this is recorded today is open, see Appendix.)
  • Config or code? Compare the deployed code version and the config version before and after the failure. Same code and different config means a config effect. Confirm by reverting only the config. Config can change with no deployment (config store, feature flag), so a config change is not always a deploy event.
  • Rollback. Redeploy the previous artifact through the pipeline, then check that the errors stop. A rollback fails or causes harm if the deployment had a database migration that the old version cannot use. Teams avoid this with backward-compatible migrations.

3.7Expected root cause

Answers: Q3.7, Q3.8, Q3.13, Q3.33

Evidence to collect before any diagnosis: the alert, metrics, logs, traces, deployments and config changes in the time window, the health of dependencies, and similar past incidents.

Mitigation and fix are different. A mitigation restores the service: revert, roll back, revert only the config, restart, scale out, turn a feature flag off, fail over, or shed load. A fix removes the cause. A hotfix is a new change and has its own risk.

3.8Supporting evidence

Answers: Q3.8, Q3.12, Q3.27, Q3.34

How engineers investigate. Compare the last working version with the current one. List recent changes. Find the affected code. Check the blast radius and connected components. Form hypotheses, and test each one by looking for evidence that would disprove it. Do not lock on the first idea. Record the hypotheses that are ruled out. Time-box each one. If several changes went out together, bisect.

Evidence that strengthens "the deployment caused it": the errors start within minutes of the deployment; the errors are only in the deployed service, and only in changed code or config paths; services that were not deployed stay healthy; a revert stops the errors.

3.9Contradicting evidence

Answers: Q3.12, Q3.27, Q3.35

Why timing alone does not prove cause. It can be a coincidence. A common cause can hit at the same time (traffic spike, dependency or infrastructure failure). The deployment may not touch the failing code path.

Evidence that contradicts "the deployment caused it" (for example when logs show a database connection failure): the database fails for other services too; errors started before the deployment; the deployment did not touch database code or config; the database's own metrics show a problem.

3.10Expected escalation behavior

Answers: Q3.9, Q3.15, Q3.16, Q3.36, Q3.37

How teams track and hand over incidents today

  • Life cycle: detected → acknowledged → investigating → fix proposed → mitigated → resolved → postmortem. Each stage has a timestamp, so time to acknowledge, mitigate, and resolve can be measured (the baseline for Artifact 1, C1). The team tracks it in a ticketing system. Postmortems are blameless.
  • Handover: the first engineer hands over a note with what is known, what was tried, and what was ruled out. The incident goes to whoever knows the component: other engineers, the manager, architects, senior leads.
  • When to stop and escalate: every source is checked and no hypothesis passes the rubric; the evidence conflicts; or the time limit is reached (20 minutes, Artifact 2).
  • When the monitoring provider is down: continue with the sources that still work, mark the evidence as incomplete, lower the confidence, and escalate if a critical source is missing. Never guess.
