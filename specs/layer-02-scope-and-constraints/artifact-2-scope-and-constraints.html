2.3Deployment boundaries

Answers: Q2.3, Q2.5, Q2.6, Q2.8, Q2.9, Q2.10, Q2.14

ItemV1 scopeLabel
User interfaceA CLI and an HTTP API. No dashboard.Decision
Platform deploymentDocker only. No Kubernetes. Scale later when the load needs it.Decision
Platform structureA modular monolith in one repository, with clear module boundaries. A module can be deployed on its own later if its load needs it.Decision
Production accessThe agent has no access to the production environment and holds no production credentials.Decision rationale: Q2.14; matches the approval rule in Artifact 1
Write pathThe agent can use write tools, but every write goes through checks and human approval. The checks are enforced outside the agent. A revert is one of two actions: (1) redeploy the last known-good artifact through the pipeline, or (2) restore the previous config version in the config store (undo: restore the newer version). A fix is a branch and a pull request that the pipeline deploys. Nothing is pushed directly to the main branch or to production.Fixed requirement source: Artifact 1 (1.5)
Emergency revert pathA revert redeploys an artifact that already passed staging and QA. It goes straight to production after human approval, with no new staging or QA run. A config restore is the same. A permanent fix takes the normal path: sandbox proof, pull request, staging, QA, production. The phase 1 limit covers only proposing the revert, not the deploy time.Decision review M1
Fix mergeThe platform opens the pull request. The human approver reviews and merges it. The merge is the approval for the fix. Branch protection on the main branch needs one human review. The platform can never merge. Detail: Layer 11.Decision review M2
SandboxA set of Docker containers, built for each incident from the same image and configuration. It holds synthetic fixtures only. It has no network route and no credentials to production. It is destroyed when the incident closes.Decision

2.6Explicit non-goals

Answers: Q2.1, Q2.7, Q2.8, Q2.9, Q2.10, Q2.11, Q2.13

  1. Multi-tenancy. It adds tenant isolation, full data isolation, per-tenant access control, more workload and model cost, rate limits, noisy-neighbour problems, queueing, and priority service for premium users. V1 serves one organization.
  2. Languages other than Python.
  3. Real incident data. V1 uses sanitized synthetic fixtures only.
  4. A dashboard. V1 has a CLI and an HTTP API.
  5. Kubernetes. V1 uses Docker.
  6. Microservices for the platform. V1 is a modular monolith.
  7. A custom or fine-tuned model.
  8. External model APIs. Incident data must not go to a new external party.
  9. A CPU fallback for the main or reviewer model. The platform escalates instead.

Answers: Q2.5, Q2.6, Q2.12, Q2.20, Q2.21, Q2.22, Q2.23

How we record decisions and assumptions

  • Every item has one label: Fixed requirement, Decision, or Assumption (Q2.20).
  • Humans only validate architecture assumptions. The AI does not, because these decisions are critical (Q2.20).
  • A decision record links to the assumptions it depends on. If an assumption fails, the decision is opened again (Q2.21).
  • Records stay in each layer's conversation log and in each artifact's decisions table. They move to ADR files (one file for each decision) later. Each record has: decision, rationale, label, owner, status, validation condition, and revisit trigger (Q2.23).
Example (Q2.21)Content
DecisionUse PostgreSQL for incident data. Rationale: industry standard, proven at large volume, supports many data types (from a literature review).
Assumption it depends onV1 data volume fits one PostgreSQL instance. Owner: Dhanush. Validate: measure data for each incident in the Q2.16 experiments.
If the assumption failsThe decision is opened again.
